# Branches — where an agent might remember an assignment

Each branch is a fork already present in `multica-jr`. The legal side is the one a CoS agent may act on. The other side is a cache, a leak, or a retired path.

Base tree: `3551e72e7` on `main`. Doctrine: the board and the queue claim are the assignment records. See [`HARVEST.md`](./HARVEST.md).

## B1 — Board versus provider memory

| Side | Where | Legal for assignment? |
| --- | --- | --- |
| Issue title, description, comments, assignee, status, properties, stages | Postgres, via `multica issue …` | Yes |
| Hermes `memories/` (`MEMORY.md`, `USER.md`, whatever the agent writes back) | `<profile>/hermes-state/<agent>/<hermes-profile>/` | No |
| Codex `memories/raw_memories.md` and `state_*.sqlite` | Per-task Codex home, and possibly `~/.codex/memories/` | No. Off unless `MULTICA_CODEX_MEMORY` is `1`, `true`, `yes`, or `on` |

Codex’s managed block is regenerated by the daemon and strips conflicting user keys inside `[features]` and `[memories]` (`server/internal/daemon/execenv/codex_memory.go`). Leaving the opt-in unset is the CoS default.

## B2 — Skill overlay versus host Hermes home

| Side | When | Memory line |
| --- | --- | --- |
| Overlay | The task carries skills. Built-in skills are appended for every agent, so this is the practical path | Agent + Hermes profile, inside the Multica profile dir. Invisible to other agents. Never reads `~/.hermes/memories` |
| Host passthrough | No skills bound, and no overlay built | The user’s real `~/.hermes`, shared by every skill-less agent, task, and issue on that runtime |

`hermes_memory.go` leaves the host path in place on purpose: closing it would break the workaround reported on #6638, and the platform-wide fix is MUL-5969 (`memory_scope`). Until that lands, a CoS fleet that wants isolated memory binds skills (the built-ins already force the overlay) and does not treat host `MEMORY.md` as anyone’s assignment book.

A different Hermes profile (`-p`, `active_profile`, or a custom `HERMES_HOME`) is a different memory line and a different session line. Same rule as Codex keying sessions on profile.

## B3 — Long-term notes versus the transcript

| Store | Key | What comes back | Idle TTL |
| --- | --- | --- | --- |
| Hermes `memories/` | agent + Hermes profile | Agreements the agent wrote into markdown. Not the transcript | 90d (`2160h`) |
| Hermes `state.db` | agent + Hermes profile + conversation (`issue id`, or `chat_<id>`) | The ACP transcript for that conversation | 14d (`336h`) |
| Codex sessions | profile hash + agent + issue id, or `chat_<id>` | Rollouts for that conversation, under `~/.codex/multica-sessions/` | Documented as matching the Hermes session store rather than the 90d memory store |

Reclaiming a session store costs a fresh thread plus a continuity notice. Reclaiming `memories/` is user-visible amnesia. Neither TTL is an assignment expiry. A deleted agent’s memory is only eventually reclaimed; the board drops the assignee when the membership path says so.

Windows without symlink privilege keeps Hermes `state.db` task-local. The daemon proves the link can be created before it moves anything. It does not copy the database, because a copy would absorb the turn’s writes into a file the next task discards (`CLI_AND_DAEMON.md`, Hermes agent memory).

## B4 — Which conversation is authoritative after a missed resume

`SessionContinuityNotice*` in `runtime_config_sections.go`. The split is “can this conversation still be read?”

| Surface | Authoritative record | Agent-facing notice |
| --- | --- | --- |
| Issue | Issue body and comments. The workflow already reads them | Re-derive unrecorded working memory. Do not open the reply by announcing a lost discussion |
| Slack | Channel history via `multica chat history` / `multica chat thread` | Same |
| Web chat, Feishu, WeCom, DingTalk | `chat_message`, via `multica chat history` | Same |
| A future surface Multica never stored | Only the current message | Tell the user, in one sentence, that this is a new session. No current surface routes here |

Poisoned or unresolvable provider sessions start with an empty `PriorSessionID` (cross-runtime, legacy 400 `invalid_request_error`, poisoned transcript). A transient failure may resume. The server may also hand back an older session with the gap flagged; the daemon resumes it. The agent then holds earlier turns and is missing the latest. The board still wins.

## B5 — How a run starts

| Source | Predicate | Parks on backlog? |
| --- | --- | --- |
| Create or assignee change | `WillEnqueueRun`, source `assign` | Yes. Backlog records the assignee and enqueues nothing |
| Status leaving the backlog category | `WillEnqueueRun`, source `status` | The transition itself is the unpark. A self-loop is suppressed |
| Comment `@mention` | Comment trigger, not `WillEnqueueRun` | Fires in any status. `@all` suppresses implicit assignee routing; an explicit mention in the same comment still fires |
| Quick-create | No issue until the single `issue create` returns | The created issue becomes the board |
| Autopilot run-only | No assigned issue for the run | Issue commands stay forbidden unless the autopilot instructions ask for them |

`AgentReadiness` is shared by autopilot admission, squad-leader dispatch, issue-assign, and the comment path. An offline direct-agent assignment still queues.

## B6 — Ownership write versus fresh handoff

| Intent | Command shape | Queue effect |
| --- | --- | --- |
| Record ownership or progress for work already underway | `issue assign` / `issue update` / `issue status` with `--no-start`, after checking the comment history for an existing claim | No new run from that write |
| Hand the issue to an agent so work begins | Assign into a non-backlog status, or promote `backlog → todo`, without `--no-start` | Enqueue, subject to B5 |
| Trusted self-assignment of the same `(issue, agent)` while a non-terminal task exists | Server suppresses the duplicate enqueue even if the client forgot `--no-start` | Ownership sticks; one run |
| Same agent, new issue (serial chain, triage batch) | Ordinary assign | A run starts. The suppression is pair-exact on purpose |

## B7 — Advisory sibling read versus queue serialization

| Question | Ask | Guarantees |
| --- | --- | --- |
| Is this issue’s work in progress, blocked, delivered? | Issue status | The column people filter on |
| Who has a non-terminal run on this issue or its family? | `multica issue runs --active` / `--siblings` | None. Cap 20. A missing stderr warning means the list was not truncated |
| May this agent pick up another run for this issue? | The queue: one active run per `(issue, agent)`, one pending slot | Yes. `SKIP LOCKED` plus the unique index |
| Should I avoid a second PR against the same code? | Sibling runs, then a comment to the other agent | The read does not reserve the files |

## B8 — Status fact versus run lifecycle

| Write | When it is true |
| --- | --- |
| `in_progress` at the start of the turn | This turn will produce part of what the issue itself asks for, and the issue is not already in an `in_progress`-category status |
| `in_review` at delivery | The issue’s own ask is delivered and waiting on a human. `done` stays human. Stage barriers and parent notifications depend on the child reaching this |
| `in_progress` at exit | Sub-issues were dispatched, or only part of the ask is delivered. A squad dispatch turn leaves the parent here until a later re-trigger confirms the goal |
| `blocked` | The agent cannot proceed, plus a comment unless identity forbids comments |
| No status write | The turn produced none of the issue’s own deliverable (question, acknowledgement, consulting on someone else’s issue) |
| Server rollback to literal `todo` | A failed issue-triggered task, and no active task or retry remains |
| Literal `done` | A human, or a merged PR whose link row has close intent |

Agent Identity outranks the workflow. An identity that forbids status writes skips those calls and continues the rest (`writeInstructionPrecedence`). Custom statuses inherit their category. The catalog in the brief is how the agent picks a key when a category holds more than one.

## B9 — Scratchpad retired

MUL-6966 removed metadata guidance from the runtime brief and from `references/issues.md`. The skill test bans the words as a teaching surface. The CLI is still reachable through `multica issue --help`. A CoS agent that needs a filterable field uses a custom property. A CoS agent that needs a narrative uses a comment. A CoS agent that needs run-local files uses the task workdir, which GC will delete.

## B10 — Env root identity versus the proposal

`ResolveRootDir` (`root_identity.go`) freezes the physical env path in `.task_roots/<hash>/root.json`. A racy second claimant re-reads the winner. A record that fails validation fails closed: the task must not mint a fresh root while the original might still hold live work. This is a path claim, not an assignment claim. Assignment still lives on the issue.

## B11 — Empty-claim cache

`ClaimTaskForRuntime` skips Postgres when `EmptyClaim` recently observed an empty queue for that runtime. Enqueue invalidates the cache in the same path (`notifyTaskAvailable`), so a new task is claimable on the next call. The cache is a poll optimization. It is not a reason for an agent to believe the board is idle.
